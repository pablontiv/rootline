# Design: Normalize analyze report kind + write analyze command doc

**Date**: 2026-07-23
**Roadmap**: T010 (kind normalization), T009 (docs/analyze.md)
**Origin**: docs-northstar audit (2026-07-22) surfaced both as documentation/consistency debt.

## Context

The `analyze` command is rootline's flagship inference command (14 detectors: 12 data + 2 governance). Two debts were found:

1. **T010** — `analyze` emits `kind: "analyze"` while every other command emits `kind: "rootline/<name>"` (`rootline/query`, `rootline/stats`, `rootline/schema-apply`, …). This is the only command breaking the JSON contract convention.
2. **T009** — `analyze` is the only major command with no `docs/<cmd>.md` reference page.

## Sequence

**T010 first, then T009.** The manual must document the final state. Writing the doc against the current `kind: "analyze"` and then renaming it would make the doc lie immediately — the exact drift the docs-northstar method exists to prevent (fix behavior before narrating it).

## T010 — kind normalization

Consumers of the string `"analyze"` (verified, exhaustive — `repair apply` does NOT check kind):

- `internal/infer/report.go:47` — producer (`NewAnalyzeReport` sets `Kind: "analyze"`).
- `cmd/rootline/schema.go:223` — dispatch probe (`if probe.Kind == "analyze"`).
- `cmd/rootline/schema.go:306` — validation inside `runSchemaApplyFromAnalyze` (`if report.Kind != "analyze"`).

Changes:

- `report.go:47` → emit `rootline/analyze`.
- `schema.go:223` → accept BOTH: `probe.Kind == "analyze" || probe.Kind == "rootline/analyze"`.
- `schema.go:306` → accept BOTH in the validation guard.

**Dual-accept rationale**: rootline auto-updates. A report generated by an older binary and saved to a file could be applied after the update; dual-accept (~4 lines) prevents that break. Reading tolerates old + new; writing always emits the new kind. This is a non-breaking change (no `!`).

Tests:

- `internal/e2e/analyze_test.go` — assert emitted kind is `rootline/analyze`.
- `internal/e2e/schema_apply_e2e_test.go` — assert `schema apply` accepts a report with the new kind, and (regression) still accepts the legacy `analyze` kind.

## T009 — docs/analyze.md

Follow the existing `docs/<cmd>.md` skeleton (purpose → flags → JSON output → examples). Every claim verified against `rootline analyze --help`, source, or real execution before writing.

Sections:

- **Purpose**: run 14 inference detectors over a directory → structured report.
- **Detectors**: 12 data (field types, enums, required, constants, link types, back-references, cross-references, section patterns, invariants, formal dependencies, traceability — plus the field-type/required/enum trio from `Analyze()`) + 2 governance (schema coverage, validation gaps). Group names taken verbatim from `analyze.go` category list.
- **Flags**: `--incremental` (report only inferences not covered by existing `.stem`), `--threshold` (section-pattern detection, default 0.60). Source: `analyze.go:34-35`.
- **JSON output**: real shape captured from execution — `version: 1`, `kind: rootline/analyze` (post-T010), `categories[]` (each with `id`, `name`, `inference_count`, `inferences[]`), `summary` (`total_inferences`, `agent_required`, `engine_resolved`). Not inferred.
- **Consumption loop**: report feeds `rootline schema apply --report <file>` (schema proposals) and `rootline repair apply --report <file>` (data-only repairs) — matches the command's own `Long:` text.

Constraints: no pinned product versions; JSON examples match real output.
